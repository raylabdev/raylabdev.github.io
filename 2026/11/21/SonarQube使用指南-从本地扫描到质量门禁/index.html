SonarQube 使用指南：从本地扫描到质量门禁

代码能编译、测试能通过，并不代表它没有隐藏的问题。空指针风险、资源未关闭、异常被吞掉、重复实现、测试覆盖不足，这些问题往往不会立刻让构建失败，却会在后续迭代中持续放大维护成本。

SonarQube 的作用，就是把这些问题变成可查看、可追踪、可纳入质量门禁的结果。本文以 Java 11 + Maven 多模块项目为例，完整走一遍本地部署、创建项目、生成 Token、执行扫描和查看报告的过程。

SonarQube 是什么

SonarQube 是一个持续检查代码质量的平台。它不只做格式检查，而是结合代码规则、编译结果和测试报告，从多个维度分析项目：

  • 可靠性：发现空指针、资源泄漏、异常处理不当等潜在 Bug。
  • 安全性：识别危险写法、安全热点和部分代码层面的安全风险。
  • 可维护性：提示重复代码、复杂度过高、无效代码等代码异味。
  • 测试覆盖率：读取 JaCoCo 等工具生成的报告，展示哪些代码没有被测试覆盖。
  • 质量门禁：根据“新代码”的覆盖率、重复率、问题数量等条件，决定一次提交能否通过。

SonarQube 不需要项目先上传到 Git。扫描器直接分析本地工作目录，再把分析结果提交给 SonarQube 服务。因此，本地开发、CI 流水线和公司统一平台都可以使用同一套分析机制。

需要注意的是，SonarQube 不能替代单元测试、集成测试、依赖漏洞扫描或专业安全测试。它更像是把这些工具产生的结果汇总起来，再结合静态代码规则形成统一的质量视图。

进入 Projects → Create Project。如果只是扫描本地代码，不需要先配置 GitHub、GitLab 等 DevOps 平台，直接选择底部的 Create a local project。

Project Key 是扫描器和 SonarQube 服务之间识别项目的唯一标识，后续 Maven 命令中的 -Dsonar.projectKey 必须与它完全一致。

主分支名称要填写项目真实的主分支。如果代码主要使用 master，这里就填 master，不要机械地保留页面默认的 main。否则 SonarQube 对“新代码”和分支基线的判断可能与实际情况不一致。

继续按页面提示选择本地分析、Maven，并生成扫描 Token。Token 通常只完整显示一次，应当立即保存到密码管理器或其他安全位置。

第三步：配置 JaCoCo 和扫描属性

SonarQube 本身不会运行测试，也不会自己生成覆盖率。它读取 Maven 测试执行后产生的 JaCoCo 报告。因此，项目需要同时完成两件事：

  1. 使用 JaCoCo 在测试过程中采集覆盖率；

  2. verify 构建全部 Maven 模块并运行测试。
  3. JaCoCo 在测试期间采集覆盖率并生成报告。
  4. Sonar Scanner 分析代码，把问题、覆盖率和重复率等结果上传到 SonarQube。

-U 表示强制检查依赖更新。日常扫描不需要每次都加；依赖刚刚变更，或者怀疑本地缓存有问题时再使用即可。

扫描时不要加 -DskipTests。跳过测试后，JaCoCo 不会产生本次测试的执行数据，SonarQube 即使收到报告，也只会看到覆盖率为零或者没有覆盖率数据。

第五步：查看扫描结果

回到 http://localhost:9000，打开 test 项目。最先查看的是项目总览中的 Quality Gate：绿色通常表示通过，红色表示未通过。点击具体条件，可以看到是新增 Bug、覆盖率、重复率还是其他指标没有达标。

接着进入 Issues 页面，按严重级别、问题类型或文件过滤。点击一条问题时，可以看到：

  • 出问题的文件、代码行和上下文；
  • 规则解释以及为什么这个写法有风险；
  • 官方给出的修复建议；
  • 问题是在本次新增代码中，还是来自历史代码。

建议优先关注 New Code，而不是一开始要求存量代码全部清零。SonarQube 的“新代码”思路强调：历史技术债可以逐步处理，但新提交的代码要守住质量底线。这样质量门禁更容易落地，也不会因为存量问题过多而让团队直接放弃。

修改代码后重新执行扫描即可。SonarQube 会更新问题状态，并在项目历史中保留趋势数据。

sonar.exclusions 和 coverage.exclusions 有什么区别

这两个配置看起来类似，但影响范围完全不同：

配置 是否分析代码 是否影响覆盖率 适合场景
sonar.exclusions 否 是 生成代码、第三方代码等确实不需要分析的目录
sonar.coverage.exclusions 是 是，只排除覆盖率 DTO、枚举、常量等不要求测试覆盖率但仍需检查 Bug 和安全问题
JaCoCo <excludes> 不由 JaCoCo 统计 是 让 JaCoCo 报告本身不包含这些类

当前材料中的配置同时使用了 sonar.exclusions 和 sonar.coverage.exclusions，并把 dto、enums、facade、constant、constants 全部排除。这意味着这些目录不仅不计入覆盖率，连潜在 Bug 和安全问题也不会进入 SonarQube 的问题列表。

如果项目只是希望这些目录不拉低覆盖率，建议只保留覆盖率排除：

对应的 JaCoCo 排除规则可以保留，用于让覆盖率报告同样聚焦业务代码。是否真的需要完全排除分析，应当根据这些目录的用途决定。若它们包含手写业务逻辑、参数校验或权限判断，就不适合直接从分析范围中消失。

常见问题

1. SonarQube 页面打不开

先确认容器状态：

如果是刚启动，等待日志出现 SonarQube is operational。如果 9000 端口已被占用，可以改成 -p 9001:9000，但扫描时 SONAR_HOST_URL 也要同步改成 http://localhost:9001。

2. 扫描提示 Token 无效或没有权限

检查三件事：Token 是否属于当前用户、sonar.projectKey 是否与网页中的 Project Key 完全一致、SONAR_HOST_URL 是否指向正确环境。Token 无效时最好重新生成，不要继续复用来源不明的旧 Token。

3. 扫描成功，但没有覆盖率

依次检查：

  • 是否跳过测试；
  • Maven 是否真的执行了 JaCoCo prepare-agent 和 report；
  • 各模块 target 目录下是否产生 jacoco.xml 或 jacoco.exec；
  • SonarQube 中配置的覆盖率排除是否过于宽泛；
  • 多模块项目是否只扫描了部分模块。

4. 排除规则没有生效

先确认扫描方式是 Maven 还是 Scanner CLI。Maven 项目应当优先检查 POM 属性是否放在父工程、模块是否继承了它，以及属性名是否拼写正确。规则修改后重新扫描，旧扫描结果不会自动重新计算。

5. 第一次扫描特别慢

首次扫描需要下载依赖、编译、运行测试、分析规则和上传结果。后续可以利用 Maven 本地仓库缓存，但不要为了速度随意跳过测试。与其跳过测试，不如把耗时测试拆分到合适的 CI 阶段，并保证覆盖率数据完整。

6. 本地容器能不能直接用于生产

不建议。本文的 Docker 启动方式适合个人体验和功能验证。正式环境需要可持久化的外部数据库、资源规划、HTTPS、备份、身份认证、Token 管理和高可用方案。

总结

SonarQube 的核心价值不是生成一张漂亮的报告，而是把代码质量变成开发流程中可以持续执行的标准：

  • 本地或 CI 中自动扫描，不需要先上传 Git；
  • 用 JaCoCo 提供测试覆盖率，用 SonarQube 汇总问题和趋势；
  • 通过 New Code 和 Quality Gate 控制新增技术债；
  • 谨慎使用排除规则，只排除真正不需要检查的代码。

对于现有的 Java 11 + Maven 多模块项目，先跑通一次 clean verify + sonar，再根据实际代码结构收紧排除规则，通常就能建立起第一版可用的代码质量检查流程。
